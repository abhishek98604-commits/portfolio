The audit: why AI tools get it wrong
Six problems

    
AI tools only see what is written down. Every gap in the system becomes a guess.

    

      
01
Figma and code drifted apart
The Figma button had 5 variants, the code had 9, and the names did not match. The AI cannot map a design to the right component.

      
02
Tokens named by value, not purpose
blue-600 says what it looks like, not when to use it. The AI picks colours by eye, so the same blue ends up on links, buttons and info banners.

      
03
Hard-coded values in product code
Years of quick fixes left hex colours, pixel spacing and !important overrides across product code. AI tools copy the patterns they find in the codebase.

      
04
Inaccessible markup
Clickable divs, inputs without labels, missing focus styles, errors shown only in red. Generated code repeats the same accessibility gaps.

      
05
Docs written only for people
Screenshots, PDFs and Storybook pages with no written rules. An AI cannot read “use this for the main action only” from a picture.

      
06
No single source of truth
Some teams kept their own copies of components and changed them. The AI finds three versions of the same card and does not know which one is right.

The fix, in four layers
What changed

    

      
01 · Tokens
Name by purpose
A purpose layer sits on top of the old colour palette. Old names still work as aliases, so nothing breaks on day one.

      
02 · Components
Match Figma to code
Every Figma variant maps one to one to a code prop, and each Figma component links to its code, so tools can see both.



      
03 · Docs for AI
Write the rules down
A short markdown file per component that people and AI tools both read: purpose, when not to use it, required props, accessibility.

      
04 · Guardrails
Catch drift automatically
Lint rules block hard-coded colours and pixel values in pull requests, and the design review agent checks screens before review.

    

  


  
  

    
Working with the design system team and developers
How the work runs

    
The technical fix was the easy part. Getting product teams to change how they work was the real job.

    

      
Audit together
One shared sheet with the design system team: every component, its Figma name, code name, and gaps found.

      
Pilot one flow
Start with one real flow, like plan selection, prove it works, then scale to other teams.

      
Review in pull requests
Designers review component code in pull requests, not just screens in Figma.

      
Contribution model
Product teams propose new components, the system team approves, so copies stop spreading.

    

    

      
Tension
“Renaming tokens will break every team.”
Resolution: keep old names as aliases, mark them deprecated in the docs, and give teams a script that replaces them automatically. Remove the old names only after usage drops to zero.

      
Tension
“Strict lint rules will slow us down.”
Resolution: start the rules as warnings, not errors. Allow a documented exception with a comment. Turn on blocking only once a team is under a small agreed number of warnings.

      
Tension
“Design and code use different names.”
Resolution: code names win, because that is what ships. Figma keeps friendly display names, mapped one to one in the component docs.
