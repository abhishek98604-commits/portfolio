Making a legacy design system AI-ready

Designers and developers now build with AI tools like Claude Code, Cursor and Figma-to-code. Pointed at an older design system, these tools guess. They hard-code colours, invent spacing and turn buttons into divs. This is how I approach fixing that: what to audit, what to review in the HTML and CSS with developers, and how to work with the design system team so the fix sticks.

The problems come from my experience with large, long-lived design systems. The before and after below uses Northstar, a sample system I built for this project. It is not Verizon code.

The audit: why AI tools get it wrong
Six problems

    
Most legacy systems work fine for people who already know them. AI tools do not have that memory. They only see what is written down, so every gap becomes a guess.

    

      
01
Figma and code drifted apart
The Figma button had 5 variants, the code had 9, and the names did not match. The AI cannot map a design to the right component.


Figma: Button / Primary / Large
Code:  <Btn kind="cta-blue" size="xl">

      
02
Tokens named by value, not purpose
blue-600 says what it looks like, not when to use it. The AI picks colours by eye, so the same blue ends up on links, buttons and info banners.


--blue-600: #2754e6;   /* button? link? info? */
--gray-300: #d1d5db;   /* border? disabled text? */

      
03
Hard-coded values in product code
Years of quick fixes left hex colours, pixel spacing and !important overrides across product code. AI tools copy the patterns they find in the codebase.


.promo-banner {
  color: #b7791f !important;
  margin-top: 17px;
}

      
04
Inaccessible markup
Clickable divs, inputs without labels, missing focus styles, errors shown only in red. Generated code repeats the same accessibility gaps.


<div class="btn" onclick="next()">SELECT</div>
<input placeholder="Email">  <!-- no label -->

      
05
Docs written only for people
Screenshots, PDFs and Storybook pages with no written rules. An AI cannot read “use this for the main action only” from a picture.


Button docs today:
  [image] [image] [image]
  “See examples above.”

      
06
No single source of truth
Some teams kept their own copies of components and changed them. The AI finds three versions of the same card and does not know which one is right.


/checkout/components/PlanCard.jsx
/shop/shared/PlanCard.jsx
/legacy/ui/plan-card-v2.jsx

The fix, in four layers
What changed

    

      
01 · Tokens
Name by purpose
A purpose layer sits on top of the old colour palette. Old names still work as aliases, so nothing breaks on day one.


// tokens.json (one file, Figma and code)
"color-action-primary": "{blue-600}",
"color-text-secondary": "{gray-600}",
"color-border-subtle":  "{gray-200}",
"space-4": "1rem"

      
02 · Components
Match Figma to code
Every Figma variant maps one to one to a code prop, and each Figma component links to its code, so tools can see both.


Primary / Large→variant="primary" size="lg"
Secondary / Medium→variant="secondary"
Text link→variant="ghost"

      
03 · Docs for AI
Write the rules down
A short markdown file per component that people and AI tools both read: purpose, when not to use it, required props, accessibility.


# button.md
Use: one primary button per view.
Do not: use for navigation, use a link.
Label: verb + object, e.g. “Select plan”.
Props: variant, size, disabled.
A11y: never remove focus outline.

      
04 · Guardrails
Catch drift automatically
Lint rules block hard-coded colours and pixel values in pull requests, and the design review agent checks screens before review.


// .stylelintrc
"color-no-hex": true,
"declaration-no-important": true,
"unit-disallowed-list": ["px"],
"scale-unlimited/declaration-strict-value":
  ["/color/", "font-size"]

    

  


  
  

    
Working with the design system team and developers
How the work runs

    
A design system belongs to a team, not to one designer. The technical fix is the easy part. Getting many product teams to change how they work is the real job.

    

      
Audit together
One shared sheet with the design system team: every component, its Figma name, code name, and gaps found.

      
Agree the rules first
Token names and the component checklist were agreed with the system team before any code changed.

      
Pilot one flow
Start with one real flow, like plan selection, prove it works, then scale to other teams.

      
Review in pull requests
Designers review component code in pull requests, not just screens in Figma.

      
Weekly triage
A short weekly session to sort new gaps: fix in the system, or fix in the product.

      
Contribution model
Product teams propose new components, the system team approves, so copies stop spreading.

    

    

      
Tension
“Renaming tokens will break every team.”
Resolution: keep old names as aliases, mark them deprecated in the docs, and give teams a script that replaces them automatically. Remove the old names only after usage drops to zero.

      
Tension
“Strict lint rules will slow us down.”
Resolution: start the rules as warnings, not errors. Allow a documented exception with a comment. Turn on blocking only once a team is under a small agreed number of warnings.

      
Tension
“Design and code use different names.”
Resolution: code names win, because that is what ships. Figma keeps friendly display names, mapped one to one in the component docs.

    

  


  
  

    
How to know it is working
Measures

    

      
Token coverage
Share of colours, spacing and type in product code that come from tokens.

      
Hard-coded values
Count from the lint report each sprint. It should only go down.

      
AI first-pass rate
How often AI-generated UI passes the lint check and review agent with no changes.

      
Time to prototype
Time from a design to a working, on-brand prototype.
