Your design system was built for people. Now it needs to work for AI too.

Abhishek Bora, Principal Designer

A few months ago I asked an AI coding tool to build a simple plan card using our design system. The result looked close enough at first glance. Then I opened the code. Six hard-coded colours. Eleven pixel values that matched nothing in our spacing scale. A button made out of a div, with no focus state and an all-caps label.

The tool was not the problem. It did exactly what our system taught it to do.

Why AI tools struggle with older systems

Most design systems that have been around for a few years work well for the people who use them every day. Those people know which blue is for buttons, which card is the real one, and which rules are written down only in someone’s head.

An AI tool has none of that memory. It reads what is in front of it: the code, the token names, the docs. Every gap becomes a guess, and guesses add up fast. In my audits, the same six problems came up again and again:

  1. Figma and code drift apart. The button has five variants in Figma and nine in code, and the names do not match.
  2. Tokens are named by value. blue-600 tells you the colour, not when to use it.
  3. Product code is full of quick fixes. Hex colours, pixel spacing and !important, copied from file to file.
  4. Markup is not accessible. Clickable divs, inputs without labels, errors shown only in red.
  5. Docs are written for eyes. Screenshots and examples, but no written rule like “one primary button per screen”.
  6. There is no single source of truth. Three copies of the same card, slightly different, in three folders.

None of these are new. What is new is that AI tools copy them at speed.

Start with a code review, not a Figma file

My first instinct as a designer was to clean up the Figma library. That helped, but it was not where the problems lived. The real work started when I sat with front-end developers and went through the component code line by line.

We used a short checklist:

  • Is every clickable thing a real button or link?
  • Does every input have a visible label?
  • Is there a visible focus state?
  • Do colours, spacing and font sizes come from tokens?
  • Are there any !important overrides?
  • Do the prop names match the Figma variant names?

Doing this together mattered. Developers saw why the design rules existed, and I learned which rules were expensive to change and which were easy wins.

Fix it in four layers

1. Tokens named by purpose. Add a layer of names that describe the job: color-action-primary, color-text-secondary, color-border-subtle. Point them at the existing palette, so nothing changes visually. Keep the old names as aliases for now.

"color-action-primary": "{blue-600}",
"color-text-secondary": "{gray-600}",
"space-4": "1rem"

2. Components that match. Every Figma variant should map one to one to a code prop. Primary / Large in Figma becomes variant="primary" size="lg" in code. Then link the two, so tools can see which code belongs to which design.

3. Docs written for both people and AI. For each component, a short text file: what it is for, when not to use it, the props, and the accessibility rules. Plain sentences, no screenshots needed.

# button.md
Use: one primary button per view.
Do not: use for navigation. Use a link.
Label: verb + object, e.g. "Select plan".
A11y: never remove the focus outline.

This is the layer that changed the AI output the most. Once the rules were written down, the tool followed them.

4. Guardrails that catch drift. Lint rules that flag hard-coded colours, pixel values and !important in every pull request. On the design side, an automated review that checks screens for contrast, spacing and tap targets before a human looks at them.

The people part is the hard part

A design system belongs to a team, and to every product team that depends on it. Three conversations come up every time.

“Renaming tokens will break every team.”

It will, if you do it in one go. Keep the old names as aliases, mark them deprecated, and give teams a script that swaps them automatically. Remove the old names only when nobody uses them.

“Strict lint rules will slow us down.”

Start with warnings, not errors. Allow documented exceptions. Turn on blocking only once a team is close to zero warnings. Nobody likes a rule that stops a release on day one.

“Design and code use different names.”

Code names win, because that is what ships. Figma can keep friendly display names, mapped one to one in the docs.

What made it work was a simple rhythm: one shared audit sheet with the design system team, one pilot flow before scaling, a short weekly triage, and designers reviewing component code in pull requests, not just screens.

How to know it is working

Four numbers are enough:

  • Token coverage: the share of colours, spacing and type that come from tokens.
  • Hard-coded values: counted by the linter each sprint. It should only go down.
  • AI first-pass rate: how often generated UI passes the checks with no edits.
  • Time to prototype: from design to a working, on-brand prototype.

In my sample system, the same prompt went from seven lint issues to zero, and token usage in the generated CSS went from none to most of it. The change was not in the AI tool. It was in what we gave it to read.

Where to start on Monday

  1. Ask an AI tool to build one common component with your system, and read the code it writes.
  2. List every guess it made. That list is your audit.
  3. Pick the one component used most, and fix it across all four layers.
  4. Run the same prompt again and compare.

A design system has always been a set of agreements between people. Now some of the readers are machines. The good news is that the things that help AI, clear names, written rules and accessible code, help every new designer and developer too.
